### Tempo de parada: ajuste antes de atualizar

Uma transmissão pode levar até 90s, e o `docker stop` mata o container em 10s. Sem um prazo maior, um deploy no meio de uma emissão corta a transmissão: a nota pode sair sem que a sua aplicação receba a resposta.

A imagem não tem como definir esse prazo: ele é de quem inicia o container. **Vale para a API e para o worker, com log ligado ou não.**

| Como você sobe | O que definir |
|---|---|
| `docker-compose.yml` deste repositório | Nada: já vem com `stop_grace_period: 120s` |
| Compose próprio | `stop_grace_period: 120s` nos dois serviços |
| `docker run` | `--stop-timeout 120` nos dois containers |
| Kubernetes | `terminationGracePeriodSeconds: 120` |

Se aumentar `ACBR_WORKER_TIMEOUT_SECONDS`, suba este prazo junto.

### `ACBR_LOG_PATH` em produção

Só afeta quem definiu essa variável. Com `MODO=producao`, `ACBR_LOG_PATH` sem `ACBR_LOG_NIVEL` passa a ter o boot recusado, porque o nível padrão grava XML e certificado em disco. Remova a variável ou defina um nível abaixo de 3.
